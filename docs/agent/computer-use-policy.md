# CPX-CUA 应用访问策略与部署

电脑控制默认关闭。开启后，应用访问依次检查可信身份、机器策略、用户策略、应用授权与任务权限。
`allow` 只表示策略通过，不是用户授权。聊天处于完全访问（有效文件权限为完全访问且审批策略为 `never`）时可直接读取和操作，不弹框，也不生成聊天或永久授权；其他 `never` 组合不自动允许。Plan 不建立新授权，仅主 Agent 可以操作。请求批准和帮我批准的首次应用授权都由用户在聊天中确认，其他工具的自动审查设置不变。UAC 不参与应用授权决策，也不会自动提权。

## JavaScript 入口与审批后续接

模型可见的电脑控制入口是宿主提供的 `mcp__node_repl__js`。每次调用都在独立子进程中执行，只暴露 `computer`
（`apps()`/`read()`/`action()`）与 `nodeRepl` 输出助手，支持顶层 `await`；不提供任意模块导入、Shell、文件、网络或
原生 Helper 凭据。进程隔离用于清理与故障隔离，不宣称 JavaScript VM 是安全沙箱。
三个内建工具（`ComputerApps`/`ComputerRead`/`ComputerAction`）保留注册身份与审计，但不再直接暴露给模型；每次
电脑操作仍回到统一注册、校验、Hook、判权与审批链，Skill 范围、插件可用性与回合冻结能力同时约束外层入口和内部操作。
首版入口仅主 Agent、聊天模式可发现和调用；子 Agent 与 Plan 不可调用。

遇到需要应用读取的场景时，当前 JavaScript 执行会结束：被阻塞的那一次读取、宿主身份与授权指纹写入现有审批
checkpoint，脚本在读取之后的代码不会继续执行。用户批准后只重新校验插件、权限、身份与窗口引用，并执行被保存的
那一次读取，其界面结果作为本次 `mcp__node_repl__js` 调用的完成结果返回；不保存也不重放脚本、子进程或 VM 状态。
拒绝、重启、断连、超时和结果未知都不会自动重放已经发生的动作。Agent 需要根据恢复结果重新观察并发起新的调用。

`node_repl` 不写入用户 MCP 配置，用户不能编辑其启动命令，也不会被同名的用户服务器替换；它只在官方内置
`computer-use` 插件启用且桌面宿主可用时出现，MCP 状态页以“宿主提供”标注归属与连接状态。开发态复用现有 Bun，
安装态通过 `pidex-agent.exe --pidex-node-repl` 的专用启动模式运行子进程，用户无需额外安装 Node 或 Bun。

## 管理员策略

Agent 只读 `%ProgramData%\Pidex\requirements.toml`，不会创建或修改它。
部署者应让 Administrators 和 SYSTEM 拥有写权限，普通用户仅有读取权限，且目录不能被普通用户替换。
品牌清零后只读取上述新目录：仍放在 `%ProgramData%\CodePilotX\requirements.toml` 的策略不会被读取，
已部署机器策略的管理员需要在升级前把文件移动到 `%ProgramData%\Pidex\`，否则电脑控制策略会静默失效。
示例使用原生发现的准确 AUMID 和证书 X.500 发布者名称；不能使用应用显示名或路径作为发布者规则。

```toml
[computer_use]
default_app_access = "deny"
allow_persistent_approval = false

[computer_use.windows.aumids]
"Microsoft.WindowsCalculator_8wekyb3d8bbwe!App" = "allow"

[[computer_use.windows.exes]]
publisher_name = "CN=Example Publisher, O=Example Publisher, C=US"
product_name = "Example Editor"
binary_name = "editor.exe"
access = "allow"
```

每个来源先匹配专属规则，未匹配才用该来源的 `default_app_access`（默认 `allow`）。同一来源的匹配规则中拒绝优先；机器和用户任一来源拒绝即禁止。未签名文件不能命中发布者规则，只使用默认策略。
存在但无法读取或解析的策略文件会禁止读取和输入，界面只显示安全的原因。缺失文件使用默认值。
策略文件和用户配置变化受到监听；策略变更停止当前控制，使旧引用失效，不重放旧命令。已经发生的输入不能撤销。

## 用户策略与授权

仓库当前的统一配置服务使用用户 `config.json`（JSONC），因此用户策略复用该服务，以 key-path 局部编辑保留未知键；不另建用户 TOML 配置或逆转现有迁移。机器策略保持 TOML。
用户配置支持对应结构：

```json
{
  "computer_use": {
    "default_app_access": "allow",
    "allow_persistent_approval": true,
    "windows": {
      "aumids": {},
      "exes": []
    }
  }
}
```

只有用户级配置参与电脑权限；项目和 profile 配置不能授予权限或放宽限制。
新版永久授权写入 `desktop.computerAppApprovalsV2`；旧 `desktop.computerAppPermissions` 原样保留。旧允许显示“需要重新确认”，重新发现后对新身份授权；旧路径拒绝仍生效，必须先明确撤销该拒绝。

任一来源的 `allow_persistent_approval=false` 会隐藏并拒绝新增永久允许。已有永久允许保留，但不能据此在新聊天中获得权限；当前有效聊天授权继续有效，永久拒绝继续生效。
首次使用在聊天应用授权卡选择“允许此对话”或“始终允许”，无需在设置中发现或添加应用。设置仅管理永久授权及已有记录；宿主断连或桌面重启后，对话授权失效。完全访问的直接访问资格不会带入需要审批的模式。

## Windows 身份

- 打包应用：核验进程注册包、包状态和签名类型、安装位置、注册应用列表中的 AUMID。
- 普通签名 EXE：WinVerifyTrust 验证嵌入签名或系统目录签名，从验证通过的证书取得发布者，并读取受签名保护的 ProductName/OriginalFilename。多签名或多语言身份有歧义时拒绝。
- 未签名 EXE：授权绑定完整文件 SHA-256。损坏或无法验证的签名不能降级为未签名文件。

每次读取和动作都重新核验进程 generation、窗口所属 PID、应用身份和文件指纹。改变后要求重新发现，结果不明不重放。签名升级身份字段不变时保留授权；未签名应用重新构建导致哈希变化时重新授权。
宿主通过 `computer.host.identity.v1` 注册可信能力；原生握手也必须声明身份核验支持。旧宿主或旧原生 exe 不可回退到路径身份执行控制。策略扩展使用 `computer.policy.v1`，通信仍为唯一的 `thread-rpc-v4`。

## 用户手动验收

UI 影响面：设置中的“任意应用”开关与“始终允许的应用”列表、已有旧授权/拒绝记录管理、上下文入口短提示、聊天应用授权卡。保留原有控制状态和停止按钮，不新增面板。

1. 完全访问：开启一次电脑控制，在聊天要求读取记事本并输入文字；无需设置添加应用或应用授权框，设置中不新增永久允许记录。
2. 切换模式：将同一聊天从完全访问切换到请求批准，读取刚才的应用应出现“允许使用应用？”；选择“允许此对话”后该聊天不再重复询问，新聊天仍需确认。
3. 帮我批准：选择此模式，首次应用读取仍由你确认；其他工具继续使用自动审查。选择拒绝后不读取和输入。
4. 永久允许：审批卡选择“始终允许”，当前读取、截图和后续动作继续正常完成。设置显示记录；撤销立即停止本回合，下一回合重新询问。旧客户端普通允许按对话授权处理。
5. 管理员拒绝：部署 deny 规则，完全访问也不能放行；修改策略后当前控制停止，旧引用失效。关闭 UAC 不影响此项测试。
6. 禁止永久授权：设置 `allow_persistent_approval=false` 后不提供“始终允许”；原记录保留但不能作为跨聊天授权使用，已明确批准的当前聊天仍可用。
7. 旧授权/已有拒绝：仅在存在记录时显示管理入口；旧允许需要重新确认，拒绝优先且保留原记录，撤销后在聊天正常授权。
8. 未签名开发应用：授权后重新构建，发现新文件身份应重新授权；签名应用正常升级且身份不变时保留授权。
9. 停止与边界：Plan 不建立新授权或执行动作，子 Agent 不能控制；其他聊天占用、停止、断连和超时不重放输入，只控制已运行应用。

验收前完整重启 Agent 和 Desktop，让审批契约与权限逻辑一起生效。无需为此修改 UAC。
