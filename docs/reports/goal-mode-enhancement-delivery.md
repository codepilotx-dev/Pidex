### 继续、等待和恢复

- verifier 的内部结构化输出新增 `continuation`（work / external-input / no-progress）和 `progress`（advanced / unchanged），分别回答“现在有可执行工作吗”和“最新一轮是否真的推进”。用户解阻步骤不再等同于 Agent 可执行步骤。证据标明较早轮次与待判断的最新轮次。
- `external-input`、`no-progress` 或没有下一步时，宿主以现有 paused 状态停止自动续跑，保留未完成目标、用量和交付物，并在时间线写明原因及恢复条件。补齐输入后需要用户明确恢复；不新增文件轮询或自动监听器。
- 有已登记的提问、审批、checkpoint 或运行子任务时继续走已有等待/唤醒机制，不混作缺输入暂停。
- 核验格式错误、Provider 错误、超时、预算不准入、缺少核验材料及重启后未知结果都不置 complete，也不因此自动创建工作轮；暂停后由用户处理原因并明确恢复，恢复才发新的核验。用户操作导致的取消或旧修订结果不能覆盖当前状态。
- 进展分类比较同一 Goal 的成功工具输入、结果及 patch，调用 ID、耗时等元数据不参与。首次调查可产生新证据；重复相同结果不算推进。核验器只能将宿主的 progress 降为 no-progress，不能仅凭模型自述升级进度；语义上等价但字符串不同的检查也可被识别为 unchanged。连续两轮 no-progress 后停止，即使 verifier 仍错误建议继续检查。子任务完成状态本身不作为实际交付证明。
- 三轮 blocked 门槛保留；它不要求为了满足门槛而自动空转三轮。宿主暂停未完成目标与模型声明 blocked 是不同动作。

### 预算变更、分工与完成判断

- 运行中仍允许放宽预算。旧/新上限、累计消耗与剩余额度在同一个 Turn 的下一次模型请求注入；已发出的请求无法即时改写，返回的旧工具安排在执行前被拦截，要求先消费最新预算再重审计划。已经执行中的工具不会被回滚。
- 主 Agent 收到通知后先核对是否已经交付，再调整剩余计划和运行子任务；可通过已有协作工具停止、引导或追加分工。追加不是新增范围，也不是要求花完额度。宿主不凭预算数字擅自重分配任务。
- 主 Agent 等待子任务时，预算变更可通过已有 checkpoint/outbox/lease 恢复同一 Turn，明确告知子任务尚未完成，由主 Agent决定如何调度；不必等所有子任务自然结束。子 Agent 在自己的下一次请求也读取最新预算通知，不能消费主 Agent 的回执。
- 主 Agent 成功响应后才确认预算通知消费，并在时间线显示“主 Agent 已收到预算变更”；流失败、取消、旧修订回执不消费。未消费通知持久保留，重启后仍可注入。该回执说明已收到，不声称已经执行所有分工调整。
- 对已经停止的 Goal，追加或取消上限前先核验原有交付：确认已交付则置 complete 并拒绝预算修改，原上限不变；有效未完成结果允许保存新预算，external-input 时明确保持暂停并说明输入条件；核验异常不保存预算，用户可明确重试。核验使用用户此次请求的新上限做准入、零重试，实际核验消耗仍计入原 Goal，即使最终拒绝预算变更也不抹掉这笔消耗。已有 complete 目标直接拒绝，不再发核验；尚无执行记录时不存在可核验的交付记录。
- 预算恢复仍在创建工作轮之前检查交付。预核验的未完成结果在目标正文未变时随控制修订转存，避免为同一次预算恢复重复付费核验；只有确认有 Agent 可执行的工作才续跑，外部输入缺失则停止。paused Goal 不因追加自行恢复。运行中的预算调整保留同 Turn 通知与重审，不在执行中额外插入独立完成核验。
- 修复单次工作请求将模型广告最大输出（如 393216）直接用于预算准入的问题。有限预算工作请求按剩余额度使用实际发送的输出上限，最高 16384，通常至少预留 4096（模型自身上限更低时沿用其上限）；仍保留输入成本和收尾预留。准入估算与 Provider 的 maxTokens 使用同一值，6000 预算的纯文本收尾仍保留。

## 实现结果

### blocked 门槛与进度分类

模型只提供 status/blocker，宿主绑定 turnId 和实际请求看到的 goalId/控制修订。前两轮候选落库后返回 N/3，第三个连续同因候选才落 blocked；同轮重试不能增加次数。完成工具仍不需要三轮，但旧请求不能完成已改动或重建的目标。blocker 归一化后为空同样拒绝。

进度分类使用工具、审批、提问、checkpoint 与子任务等宿主事实。等待不排轮询续跑；文字交付先接受 verifier 判断，再应用无进度暂停。原有活动 turn 的 Stop、Goal 状态操作、预算/目标变更与模式切换保留原有语义并维护控制修订。

### 结算、并发与恢复

- finalizeTurn 原子提交 turn、计量、outbox 和待协调观察，不再提前做无进度暂停。
- 协调器领取整个观察，覆盖核验和最终决策；重复回调不能绕过正在运行的核验提前排队。
- 核验返回后在事务内重读 goalId、控制修订、Goal 状态、最新 turn、活动/排队输入、归档和队列暂停状态。通过、不通过和错误都不能覆盖用户的新操作。
- 核验监听宿主事件取消；源 turn 已完成后的 Stop 也能取消核验并暂停 Goal。
- complete/paused 与 Goal、目录更新事件在同一事务内提交，再发布。续跑创建后发布 turn/queue/agent 事件并通知 ThreadService 实际执行，避免 active + queued 却无人启动。
- 观察按 pending → claimed → settled 处理。重启恢复未处理观察和已领取的结算，未知结果的核验记 interrupted，不重复发出模型请求，并暂停等待用户明确恢复；早期实现遗留的“已 settled 但无任何后续决策”记录可恢复处理。
- 启动排队的自动续跑前重新核对目标身份/状态并重建当前 objective；旧目标的核验参考不沿用到新目标。

### verifier 与证据

复用来源 turn 的会话模型和 pi-ai 结构化输出设施。独立调用不执行业务工具、不创建 subagent/伪 turn；最多 1024 输出 token，模型请求重试为 0，超时 30 秒。异常、坏 JSON 和取消均不是通过。

核验输入包含当前 Goal 生命周期内截至来源 turn 的有界工具输入/输出、文件变更、交付文字及计划，使用统一脱敏与 XML 转义。证据最多 100 项，摘要最多 24000 字符；助手自述标为待核验主张，截断不能视为交付证据。只有确认存在可执行工作的 false 结果，其 reason/nextAction 才作为转义的低信任参考加入续跑，不赋予工具权限或改变目标。

verifier 通过预算准入，输入估算、1024 输出上限及收尾预留必须同时装入剩余额度；不足时不调用 Provider。返回的实际 usage 经既有 item-usage ledger 幂等计量，审计关联 usage item。即使用户取消或 clear 后重建，已发生消耗仍属于捕获的原 goalId，并更新归档目标，不转嫁到新 Goal。

### 预算收尾

使用同一预算算术判断工作请求、其输出上限和收尾所需额度；额度不能容纳下一工作请求及预留时提前收尾，连收尾输入 + 1024 输出都不够时只发宿主拒绝提示。

收尾每控制修订领取一次，在同一个精简 Provider 请求中注入收尾指令、移除工具、设置 1024 输出上限及零重试；工具执行入口也拒绝模型凭空返回的工具调用。收尾完成/失败后按身份和修订重校验落 budget-limited，不运行 verifier 或继续 Goal 续跑。Stop、改目标和预算变更不会被旧收尾覆盖。模型调用与宿主预算拒绝文案保持分离。

### 预算只允许放宽

预算从 Goal 实际落库时起成为稳定执行条件，之后只能放宽：

| 当前预算 | 操作               | 结果                     |
| -------- | ------------------ | ------------------------ |
| 尚未创建 | 有限预算或不限额   | 允许                     |
| 有限     | 增加总上限         | 允许（界面为“追加预算”） |
| 有限     | 取消上限           | 允许，此后不能重新设限   |
| 有限     | 降低总上限         | 拒绝                     |
| 不限额   | 设为有限           | 拒绝                     |
| 任意     | 不变或省略预算字段 | 保持原值                 |
| 已完成   | 实际改变预算       | 拒绝，不重开目标         |

规则由 `@pidex/shared/thread` 的 `threadGoalBudgetViolation` 单点定义，Agent 的 `set` 与 queued Goal admission 共用同一检查（`resolveBudget`/`assertBudgetWidens`），排队消息不能绕过。降额及重新设限使用现有 `INVALID_REQUEST` 在写入前拒绝，不改动正文、状态、修订、预算、入队意图或事件；非法排队意图在启动时按最新 Goal 重新校验，失败沿用既有的 admission 失败展示，不静默应用或丢弃。

`thread/goal/set` 的 `tokenBudget` 仍是总上限而非追加量，`null` 取消上限，省略表示保留；未新增 RPC、公开状态或数据库字段，也不迁移历史预算。追加或取消上限仍推进控制修订，使旧的 verifier、收尾结果失效；所有消耗继续累计到同一 `goalId`。受限目标经修改前核验确认尚未完成后，仅在新上限高于累计用量或取消上限时恢复 active，paused、blocked、usage-limited 不会因追加自动恢复。

桌面端编辑目标不再提供任意修改总额的输入：正文单独保存且省略预算字段，预算操作走独立的“追加预算”（输入新增 Token 数，预览追加后上限与剩余额度，加法溢出禁止提交）和“取消预算上限”。不限额与已完成目标只读。`setSessionGoal` 的 `budgetBaseline: { goalId, tokenBudget }` 在修改已有预算时必传，创建、同值或仅改正文时可省略；客户端在写入前重新读取并核对身份与预算，基准变化或 RPC 冲突时刷新并要求重试，不自动重算或重试追加；追加成功后清空输入，失败保留输入，用量刷新不清除草稿，切换 goalId 时重置。

### 目标变更消费

静态、动态和续跑规则使用英文，objective 原样作为转义数据，用户可见预算提示中文。每次模型请求捕获真实 goalId、控制修订和最新 objective_revision。仅在成功的 assistant message 被 Harness 接受后确认消费；HTTP 2xx 不是消费确认。响应失败、流中断、取消不确认；旧请求不能确认更新的目标或新 goalId。连续多次改目标可以直接确认本次真正看到的最新修订。

## 2026-11-02 CUA 缺陷复核与修复

参考外部验收报告 `F:/CodeProject/guardian-lab/src/goal-enhancement-cua-20261102-1842/goal-enhancement-20261102-1842.md`，该目录仅只读查看。本轮未重复真实模型 UI 验收，下面的修复证据为生产执行链配合 faux Provider 的集成回归。

- **G04-A 暂停被 complete 覆盖**：`applyModelTerminal` 只核对身份、修订和来源 Turn，没有要求当前 Goal active。暂停后的下一请求可以捕获最新修订，因此修订校验不足以保护暂停。现增加 active 门槛，complete 和 blocked 均拒绝；暂停不强制中断当前 Turn，Turn 自然结束也不能改变 paused。
- **G07 追加后又受限**：预算更新本身已正确按累计消耗恢复 active；旧准入拒绝的迟到处理、以及旧 Turn 的预算终止结算没有绑定当时的控制修订，继续使用强制 budget-limited 语义覆盖了新预算。现将捕获的 goalId/revision 从拒绝传到错误和终止结算，两次写入均重校验；拒绝状态与提示同事务提交。不能简单取消强制受限，因为余额大于零但装不下下一次请求仍应受限。追加发生在旧 Turn 结束前时，首次恢复因有活动 Turn 不排队，旧 Turn 结束后补恢复。集成复现 51,000 → 200,000、已用 83,763，验证第二轮实际启动、用量不重置。
- **G01 一直只有拒绝提示**：发现可独立复现的结构性原因：收尾沿用完整历史、system 和工具定义估算输入，且上下文超限/压缩先于收尾准入；即使短摘要足以装入余额，也可能直接拒绝或先消耗压缩额度。不能仅归因于 CUA 操作慢。现每次准入使用独立的精简收尾投影估算：短宿主规则、当前 objective/预算、最近最多 24 条脱敏且去思考的证据，输入最多估算 3,072 Token，并受剩余额度减 1,024 输出限制。摘要准入先于自动压缩，使用该投影、无工具、零重试，不重写 session 历史。32 万字符输入回归可获得真实 Harness 返回的收尾正文。历史四次尝试未逐次重放，不能据此宣称它们全由同一原因造成；实际消耗一次跨越全部余量后仍只能拒绝，预算估算不构成硬性计费上界。
- **G08-B verifier 假通过**：仅遵守“不创建输入”的约束，被当成最终交付完成。现在结构化结果必须逐项列出 deliverable / constraint / dependency 及完成证据；宿主要求至少一个已完成且有证据的交付项，全部列出项均满足，才接受 pass。缺输入、失败读取、正确等待和不创建文件均不能替代交付。真实结构化调用回归返回“只有约束但 passed=true”，协调器审计为 fail，不置 complete；正常文字交付仍允许通过。此规则不能保证模型永不漏列需求或伪造语义判断，也不拦截 active Goal 的模型主动 complete。
- **预算只允许放宽独立核对**：共享单点规则、服务端 set、排队启动重校验、累计计量及预算冲突处理均保留。补齐服务层非负安全整数校验，直接调用也不能写 NaN、Infinity、小数或溢出值；桌面端实际修改已有预算时必须提供 goalId/原预算基准，漏传不发 RPC 写入。相同值和省略字段不受此新增检查影响。

## 人工验收影响面与限制

本轮 UI 影响面：侧栏 Turn 终态/未读点即时更新；Composer 的 Goal 暂停、恢复、完成与累计时长同步；等待阶段不继续外推，时长 tooltip 明确累计口径。保留 external-input 追加成功后的时间线说明与暂停语义。由用户手动验收，未以 Computer Use 代点界面。

人工验收影响面：blocked 连续门槛；登记等待与唤醒；文字交付自动核验；无进度暂停；真实预算收尾；创建时预算输入；追加预算预览与取消上限；正文独立保存；受限恢复；并发冲突；切换聊天后的状态同步；运行中改目标；Stop/clear/新输入期间核验返回；重启未结算 Goal。

- verifier 增加需求分类及证据结构门槛，但仍可能漏列需求或误判证据；active Goal 的模型主动 complete 仍不经过独立核验，paused 等非 active 状态不能由模型置终态。
- 同义 blocker 不做语义合并；真实等待仅支持已有宿主可恢复任务，不新增轮询器。
- 输入预算依赖估算，实际 usage 如实计量，不承诺 Provider 绝不超预算。
- 固定预算与追加机制不能保证额度不足时交付完整成果；需要更严格的新预算时使用暂停/停止、清除归档并新建阶段目标，本次不提供自动阶段切换。
- 未知结果的核验调用重启后不重发，暂停等待用户处理原因并明确恢复。
- 未提供独立核验模型配置。证据超出条数或字符上限时会遗漏，按证据不足处理，不能据此证明完成。
- 用户上一轮补测已取得真实收尾正文；本轮代码仍未重新执行真实 UI 验收。重点影响面为缺输入停止与恢复、核验异常、有限预算追加后实际工作、运行中预算通知与等待子任务时重审分工。
